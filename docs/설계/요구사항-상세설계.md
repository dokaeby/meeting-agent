# Meeting Agent 요구사항 및 상세설계 — 검토 초안

- 작성일: 2026-11-10 (Asia/Seoul)
- 예정 구현 위치: `C:\Users\Playdata\aio4\meeting-agent`
- 상태: 사용자 설계 승인 대기. 제품 코드·의존성 설치·외부 발송은 시작하지 않음.
- 확정: 여러 회사가 가입하는 SaaS, React + FastAPI, React MVVM, 기능별 모듈화, 자동화 테스트.
- 이하 명시한 기본값은 설계자의 제안이며, 사용자가 개별 승인한 사항으로 해석하지 않는다.

## 1. 목적과 완료 기준

회사가 가입하고 직원을 초대하여 Zoom을 연결하면, 회의 후 녹음/녹취를 수집하고 한국어 회의록을 생성한다. 담당자와 수신자를 확인하여 이메일과 카카오톡으로 전달한다. 웹은 설정·검토·이력 확인을 담당하며, 처리와 발송은 별도 서버 프로세스가 수행한다.

완료는 로컬 기능 구현, 자동화 검증, 자격증명을 연결한 실제 연동 검증을 구분한다. 자격증명이나 플랫폼 심사가 없다는 이유로 실제 발송 성공을 주장하지 않는다. 자동 발송 기능 구현은 개발 중 실제 고객에게 발송할 권한을 의미하지 않는다.

주요 인수 기준:

1. A회사 사용자는 B회사의 ID를 알아도 회의·문서·작업·인증정보를 조회하거나 수정할 수 없다.
2. 가입 → 이메일 확인 → 회사 생성 → 직원 초대 → 로그인 → 설정이 동작한다.
3. Zoom OAuth와 서명 검증된 완료 웹훅으로, 연결한 호스트의 대상 회의를 수집한다.
4. 한국어 녹음/녹취에서 근거가 있는 요약·결정·할 일을 만들고 웹과 PDF로 제공한다.
5. 이름이 모호한 담당자, 불명확한 기한, 검증 실패가 있는 결과는 자동 발송하지 않는다.
6. 검토자가 수신자와 문서 버전을 승인하면 수신자별 이메일·카카오 발송 결과가 남는다.
7. 웹을 닫거나 작업자를 재시작해도 DB에 저장된 작업을 복구한다.
8. 실패·중복 웹훅·중복 클릭·토큰 만료·외부 API 제한에 대한 테스트가 통과한다.
9. React MVVM 의존성 규칙과 기능 모듈 경계를 정적 검사 및 테스트로 검증한다.

## 2. 검토한 접근과 결정

| 방식 | 장점 | 비용 및 단점 | 결정 |
|---|---|---|---|
| Django 통합 웹 + 작업자 | 계정·관리 기능을 활용하기 쉬움 | React와 API 분리를 우선하는 요구와 다름 | 미선택 |
| React + FastAPI + 별도 작업자 | 화면·업무·외부 연동을 독립 검증, 향후 앱 연동 가능 | 인증과 두 런타임의 운영을 직접 구성 | 사용자 선택 |

단일 저장소에 프런트와 백엔드를 둔다. 서버는 기능 모듈을 갖춘 단일 애플리케이션과 별도 작업자로 시작한다. 마이크로서비스, 다중 LLM 에이전트, 범용 워크플로 편집기는 도입하지 않는다. 음성 인식·요약은 AI가, 권한·수신자·승인·재시도는 결정적인 코드가 담당한다.

## 4. 회사·사용자·권한

User는 전역 계정, Organization은 회사, Membership은 회사별 역할이다. 한 사용자가 여러 회사에 속할 수 있으나 API 요청 하나는 선택한 회사 하나에만 속한다. 이메일 도메인이 같다는 이유로 자동 가입시키지 않는다.

| 동작 | 회사 관리자 | 회의 관리자 | 일반 직원 |
|---|---|---|---|
| 회사 설정·직원 초대·연동 정책 | 가능 | 불가 | 불가 |
| 본인 Zoom·카카오 연결 | 가능 | 가능 | 카카오만 |
| 회사 전체 회의 관리·발송 승인 | 가능 | 가능 | 불가 |
| 수신자로 지정된 회의 열람·PDF 다운로드 | 가능 | 가능 | 본인 지정 회의만 |
| 사용자·연동 비밀값 원문 조회 | 불가 | 불가 | 불가 |

회사 생성자는 관리자. 마지막 관리자의 삭제/강등을 금지한다. 초대는 대상 이메일에 묶인 단기 일회용 토큰으로 수락한다. 계정 활성화와 암호 재설정도 해시로 저장한 일회용 토큰을 쓴다. 회사 탈퇴/비활성화는 해당 회사 세션·문서 접근·대기 발송의 권한 확인에 즉시 반영한다.

일반 직원은 현재 수신자로 지정되어 있고 열람 가능 상태로 공개된 확정 버전만 볼 수 있다. 지정만으로 초안·원문 녹취·다른 직원의 발송 이력을 보지 못한다. 관리자/회의 관리자만 초안과 원문을 본다. 수신자 제외 또는 membership 비활성화 시 과거 링크도 접근을 차단한다. 이메일로 이미 전달한 첨부까지 회수할 수는 없다.

로그인은 Argon2id 비밀번호와 서버 저장 세션, HttpOnly/Secure/SameSite 쿠키를 사용한다. 변경 요청은 CSRF 검증한다. 브라우저에 OAuth 토큰/API 키를 저장하지 않는다. 이메일 확인 전에는 외부 연동·파일 처리·발송을 허용하지 않는다. 가입·로그인·재설정은 레이트 리밋을 적용하며 계정 존재 여부를 노출하지 않는다.

## 5. 사용자 흐름과 웹 화면

1. 가입·이메일 확인 → 회사 생성 또는 초대 수락 → 회사 선택.
2. 관리자: 보관 정책·수신자·발송 규칙 설정. 호스트: Zoom OAuth 연결.
3. 회의 관리자: 자동 수집을 활성화할 호스트/회의를 선택하거나 파일 업로드.
4. 서버: 녹음 준비 → 전사 → 구조화 요약 → 담당자 매칭 → 문서 생성.
5. 웹: 회의록·원문 구간·담당자·기한·수신자를 검토하고 새 버전을 저장.
6. 승인 후 발송 또는 회사가 허용한 자동 발송. 수신자별 상태·오류 확인.

화면: 로그인/가입/재설정, 회사 선택/초대, 대시보드, 회의 목록/등록, 회의 상세/원문/회의록 편집, 발송 검토/이력, 직원 관리, 연동/보관/자동화 설정.

한국어 UI, PC와 모바일 반응형, 키보드 탐색, 명시적인 처리·빈 상태·오류 표시를 제공한다. 회의록에 없는 담당자·기한은 빈 값과 ‘확인 필요’로 표시한다. 요약 내용은 HTML로 신뢰하지 않고 텍스트로 렌더링한다.

## 6. React MVVM 상세설계

React + TypeScript + Vite를 사용한다. 기능별로 Model/ViewModel/View/API를 함께 배치한다. 거대한 전역 계층이나 모든 작업에 대한 인터페이스는 만들지 않는다.

```text
frontend/src/
  app/                 # 라우팅, 인증/회사 컨텍스트, 공통 공급자
  shared/              # 공통 UI, HTTP 클라이언트, 시간/오류 처리
  features/
    auth/
    organizations/
    members/
    meetings/
      model/           # 타입·순수 검증·매핑·권한 표현
      api/             # MeetingsRepository와 HTTP 구현
      viewmodels/      # useMeetingListVM, useMeetingDetailVM
      views/           # 페이지·프레젠테이션 컴포넌트
      tests/
    minutes/
    deliveries/
    integrations/
    settings/
```

- Model: React/DOM/HTTP에 의존하지 않는 타입과 순수 업무 함수.
- Repository: 입출력이 명시된 비동기 API. 인증·CSRF·타임아웃은 공통 HTTP 계층이 담당.
- ViewModel: 테스트 가능한 React hook. 검색/정렬/편집 상태, 권한별 동작, 제출·오류·로딩을 노출한다. 문서/PDF 생성이나 외부 서비스 호출은 서버에 요청한다.
- View: ViewModel의 상태를 표시하고 동작을 호출한다. fetch/axios/저장소 접근·업무 규칙을 넣지 않는다.
- 서버 상태는 TanStack Query, 폼은 기능 범위 상태로 관리한다. 별도 전역 상태 라이브러리는 필요할 때만 검토한다.
- 회사 전환 시 query key에 organization ID를 포함하고 이전 회사 캐시·구독을 정리한다. 미확인 세션에서 이전 화면 데이터를 잠깐 보여주지 않는다.
- ViewModel은 Repository를 주입받아 hook 테스트에서 외부 호출 없이 검증한다. View 테스트는 ViewModel의 표시 계약을 검증한다.
- 다른 기능의 내부 파일 직접 import를 금지하고 공개 진입점으로 연결한다. ESLint 경계 규칙으로 Model의 React/API 참조와 View의 API 직접 참조를 차단한다.
- OpenAPI에서 생성한 전송 타입을 API 경계에서 사용하고, 화면 전용 Model은 의미가 다를 때만 별도로 만든다.

## 7. 서버 구성·모듈

제안 스택: Python 3.12+, FastAPI, Pydantic, SQLAlchemy, Alembic, PostgreSQL, Celery, Redis, S3 호환 비공개 저장소. 개발은 Docker Compose의 PostgreSQL/Redis/MinIO/mailpit를 이용한다. SMTP는 개발 mailpit와 운영 발송 서비스로 설정을 분리한다. PDF는 한국어 글꼴을 포함한 서버 렌더러로 만든다. 정확한 패키지 버전은 구현 전에 지원 버전을 확인해 lockfile에 고정한다.

```text
backend/src/meeting_agent/
  api/                 # FastAPI 라우팅, 세션/회사 의존성
  modules/
    identity/          # 가입·세션·초대·역할
    organizations/     # 회사·직원·정책
    meetings/          # 회의·입력 파일·녹취
    minutes/           # 요약·근거·버전·PDF
    deliveries/        # 승인·발송·상태·재처리
    integrations/      # Zoom·Groq·SMTP·카카오 어댑터
  jobs/                # 단계별 작업·outbox 발행·보관 정리
  infrastructure/      # DB·저장소·암호화·설정·로그
backend/tests/         # 단위·통합·계약·보안 테스트
config/                # 로컬 실행·배포 구성
docs/                  # 요구사항·설계·계획·운영·검증 기록
```

API 서버는 인증/조회/설정을 처리하고 짧게 응답한다. 작업자는 다운로드·전사·요약·PDF·발송을 수행한다. 정기 작업은 outbox 재발행·만료 작업 회수·보관 삭제를 실행한다. Redis 장애 때도 업무 상태와 outbox는 PostgreSQL에 남는다. 개발용 fake 어댑터는 명시적인 모드에서만 사용하고 화면과 응답에 표시한다. 운영에서 조용히 fake로 대체하지 않는다.

## 8. 데이터 모델과 회사 격리

주요 엔터티:

| 엔터티 | 주요 필드/규칙 |
|---|---|
| User / Session | 이메일, 해시 비밀번호, 이메일 확인 시각 / 만료·폐기 |
| Organization / Membership | 회사, 정책 / 사용자·역할·활성, 회사별 유일 |
| Invitation | 회사·대상 이메일·역할·토큰 해시·만료·사용 시각 |
| Integration | 회사·소유 직원·provider·외부 account/user ID·암호화 토큰·scope·만료·상태 |
| Meeting | 회사·host·Zoom UUID·제목·시작 UTC·IANA timezone·수집 상태 |
| MeetingRecipient | 회의·직원·채널·수신 범위, 승인된 스냅샷 |
| Artifact / TranscriptSegment | 회사·회의·비공개 키·해시·종류·크기 / 구간·시간·화자·텍스트 |
| MinutesVersion / ActionItem | 회사·회의·버전·요약·모델 정보·검토 상태 / 담당자·기한·근거 |
| Approval / Delivery | 승인자·버전·수신자 스냅샷 / 채널·대상·상태·외부 ID·시도 이력 |
| WebhookReceipt / Job / Outbox | 이벤트 중복 키 / 단계·시도·리스·다음 실행 / 발행 상태 |
| AuditEvent / UsageCounter | 회사·주체·작업·대상·결과 / 기간·전사時間·토큰·저장량 |

회사 데이터의 모든 테이블에 organization_id가 필수다. 관련 테이블은 회사 ID를 포함한 복합 외래키/유일성 제약으로 교차 회사 참조를 차단한다. API는 세션 사용자와 현재 membership으로 회사를 결정한다. 본문의 organization_id를 신뢰하지 않는다. 알 수 없거나 접근 불가한 객체는 동일한 404를 반환한다.

PostgreSQL RLS를 방어 계층으로 적용한다. 요청/작업 트랜잭션마다 SET LOCAL로 회사 컨텍스트를 설정한다. 앱/작업 DB 역할은 테이블 소유자·superuser·BYPASSRLS가 아니며 RLS 강제를 사용한다. 컨텍스트 없는 회사 데이터 접근은 거부한다. 가입·세션·회사 선택을 위한 전역 식별 테이블과 검증된 웹훅을 Integration에 매핑하는 최소 디렉터리는 예외로 명시하고, 자격증명·문서 데이터는 반환하지 않는다. 스케줄러도 회사 목록을 순회하고 회사 트랜잭션을 연다.

인증된 다운로드도 권한을 재검증해 서버로 스트리밍한다. 이메일 첨부/PDF는 발송 뒤 회수가 불가능하므로 승인 화면에 이를 표시한다. 이메일/톡 링크는 로그인 후 권한 있는 직원만 열 수 있다.

## 9. Zoom 수집과 입력 처리

- SaaS는 General App의 OAuth authorization code 흐름을 사용한다. 회사 ID·사용자·만료·일회용 nonce에 묶은 state를 검증하고 서버에서 코드를 교환한다.
- 첫 버전은 user-managed 호스트 연결. 회사 관리자/회의 관리자가 자신의 Zoom을 연결한다. 회사별 여러 호스트를 지원하되 같은 Zoom account ID를 여러 회사에 연결하지 않는다. 다른 계정 추가는 새 회사 관리자의 연결 확인을 거친다.
- 앱의 개발/테스트 자격증명과 외부 회사용 배포·심사 조건을 구분한다. 운영 공개를 코드 구현 완료와 혼동하지 않는다.
- 웹훅 challenge·서명·타임스탬프를 검증한다. payload의 tenant 값은 사용하지 않고 검증된 외부 account/user와 Integration으로 라우팅한다. 미연결/연결 해제 호스트는 수집하지 않는다.
- recording.completed는 녹음 확보, recording.transcript_completed는 녹취 확보 신호다. 녹취와 녹음 이벤트 순서가 달라도 동일 회의로 합친다. 회의 종료 즉시 녹취가 있다고 가정하지 않는다.
- 한국어 회의는 Zoom 녹취 가용성을 가정하지 않는다. 사용 가능한 녹취를 우선하고, 없으면 설정된 대기 이후 녹음 파일을 Groq STT로 전사한다. 화자는 확인할 수 없으면 ‘화자 미상’이다.
- 외부 파일은 HTTPS와 provider별 허용 호스트·리다이렉트 정책으로 다운로드한다. 사설/loopback/metadata 주소로 접근하지 않는다. 재인증 파일 URL에는 토큰을 로그에 남기지 않는다.
- 업로드는 최대 200MB, 음성 최대 120분을 초기 제안 상한으로 두고 서버·도구 양쪽에서 제한한다. 전사는 provider 한도에 맞게 압축/분할하며 ffmpeg는 인자 배열·타임아웃·자원 제한으로 실행한다. 긴 녹취는 근거 ID를 유지해 구간 요약 후 통합한다.
- 파일 형식·실제 콘텐츠·길이를 검증하고 원래 파일명을 저장 경로로 사용하지 않는다. 업로드 회의도 동일한 처리·권한·발송 경로를 사용한다.

## 10. AI와 문서 품질

Groq 키는 서비스 운영자 설정으로 서버에서만 사용한다. 회사별 사용량을 제한하고 API 모델 ID는 설정으로 주입한다. 무료 플랜은 개발용 초기 선택이며 다중 회사의 운영 용량을 보장하지 않는다. 429/일시 장애는 제한된 backoff, 영구 오류는 검토 가능한 실패로 표시한다.

LLM 출력은 JSON schema로 제한하고 Pydantic으로 검증한다. 필드: 회의 제목, 요약, 논의 항목, 결정사항, action items(담당자 후보/기한 원문/확정 기한/근거 segment IDs), 불확실성. 출처에 없는 담당자·날짜는 생성하지 않는다. 근거 ID가 실제 녹취에 있는지 검증하고 인용 텍스트는 원문에서 서버가 가져온다. 본문은 신뢰할 수 없는 데이터로 취급하며 본문의 지시로 수신자·권한·도구 호출을 변경하지 않는다.

구조·참조 검증은 의미적 정확성이나 누락/환각 부재를 보장하지 않는다. 요약·결정·할 일에는 근거 구간을 요구하지만, 모델 confidence를 발송 승인 근거로 사용하지 않는다. 첫 버전에는 의미적 정확성을 보장한다는 자동 판정을 두지 않는다. 자동 발송 활성화 시 사람이 검토하지 않은 AI 결과라는 점을 관리자에게 알리고, 문서에도 AI 생성 여부를 표시한다.

할 일 담당자 매칭은 같은 회사의 활성 직원 중 검증된 이메일·별칭 기준으로 한다. 이름 중복은 수동 매칭한다. Zoom 표시 이름만으로 메일 주소를 추정하지 않는다. 상대 날짜는 회의의 시간대·시작일로 계산하고 모호하면 비워 둔다.

회의록은 웹용 구조화 데이터와 PDF를 같은 버전에서 생성한다. 한국어 글꼴, 긴 표 줄바꿈, 페이지 넘김, 근거 구간·생성/수정 시각을 검증한다. 확정 버전은 수정하지 않고 새 버전을 만든다. 승인과 발송은 특정 버전+수신자 목록+채널 설정 해시에 묶는다. 변경하면 재승인이 필요하다.

## 11. 발송 정책·카카오 연결

기본은 검토 후 발송. 회사 관리자가 자동 발송을 켜더라도 회의별 수신자 사전 지정, 담당자 확인, 문서 검증 통과, 회사 사용량·수신자 상태 확인을 모두 만족해야 한다. LLM이 수신자를 새로 추가하지 못한다.

자동 발송 승인은 관리자가 명시적으로 켠 발송 정책의 버전에 근거한 system_policy Approval로 저장한다. 이 기록은 정책을 활성화한 관리자·정책 버전·문서 버전·수신자/채널 스냅샷·검사 결과를 포함하고 사람의 내용 검토 승인과 구분한다. 자동 처리에서 담당자 확인은 직원이 확인한 이메일/별칭의 유일한 결정적 일치만 의미한다. 추측·동명이인·모호한 날짜·근거 없는 항목·스키마 실패·불확실성 표시가 하나라도 있으면 review_required로 전환한다. 정책 비활성화/변경, 승인 주체의 권한 상실은 대기 system_policy 승인을 무효화하고 다시 평가한다. 이는 의미적 정확성 보장이 아닌 관리자가 선택한 발송 정책임을 UI에 명시한다.

첫 버전은 사전 등록된 내부 직원에게 동일한 승인 회의록을 보내고 담당 업무를 별도 섹션으로 표시한다. 개인별 비공개 회의록 분할은 후속 범위다. 회의 수신자는 참여자와 다를 수 있으므로 명시적으로 선택하고, 기본 자동 발송 대상은 회의 참여/열람 권한이 확인된 직원으로 제한한다.

이메일은 서비스 발송 주소에서 보낸다. 사용자 메일함 읽기 권한은 요구하지 않는다. 운영 SMTP 제공자와 발송 도메인 인증은 배포 설정에서 준비한다. PDF 첨부와 로그인 링크를 제공하며 첨부 크기 초과 시 링크만 보낸다.

카카오 첫 버전 제안: 각 직원이 카카오 OAuth로 본인 계정을 연결하고 본인 토큰의 ‘나에게 보내기’로 수신한다. 고객이 등록한 임의 전화번호·단체방으로 보내지 않는다. 카카오 앱 동의 항목·권한·쿼터 및 실제 동작은 설정한 앱으로 확인한다. 미연결/철회 직원은 카카오 채널을 미사용 처리하고 이메일 발송 결과와 구분한다. 기업 알림톡은 사업자/채널/템플릿 계약을 별도로 정한 뒤 확장한다.

본인 계정 연결이 회사 membership을 부여하지 않는다. 사용자 전역 카카오 식별자와 회사별 사용 동의를 구분하고, 회사를 바꿔도 다른 회사 문서를 발송하지 못한다.

## 12. 작업 상태·멱등성·실패 복구

회의 파이프라인: registered → waiting_source → transcribing → summarizing → rendering → review_required/ready → completed. 단계 실패는 failed와 실패 단계·재시도 가능 여부로 보관한다. 발송 상태는 별도로 관리한다.

Delivery: pending → sending → accepted / retry_wait / failed / unknown / cancelled. accepted는 provider가 요청을 접수했다는 뜻이며 수신함 도착·열람을 보장하지 않는다.

DB 트랜잭션으로 상태 전이와 outbox를 함께 저장한다. 큐는 at-least-once이며 작업은 단계·입력 버전·회사별 유일 키와 compare-and-set으로 멱등 처리한다. Job은 DB 리스와 fencing token으로 갱신하여 만료된 작업자의 결과 확정을 거부한다. 외부 호출 중에는 DB 트랜잭션을 길게 유지하지 않는다.

전송 직전 다시 membership·승인·문서 버전·삭제 상태를 확인한다. 수신자×채널×문서 버전당 Delivery를 유일하게 만들고 동시 발송을 잠근다. provider가 지원하면 멱등 키를 사용한다. SMTP/카카오처럼 외부 접수와 DB 기록을 원자화할 수 없는 구간은 exactly-once를 보장하지 않는다. 응답 타임아웃이나 발송 후 작업자 종료는 unknown으로 표시하고 무조건 재발송하지 않는다. 확인 후 수동 재시도에는 중복 가능성을 표시한다.

연동 해제는 해당 자격증명을 사용하는 신규 외부 호출을 차단한다. 이미 회사에 저장한 입력은 소유 직원의 탈퇴와 무관하게 회사 정책에 따라 처리할 수 있으나, 회사/회의 삭제는 이를 취소한다. 시작한 직원의 탈퇴만으로 다른 직원이 승인한 회사 소유 작업을 모두 취소하지 않는다. 대기 중인 개인 카카오 발송과 탈퇴자 수신 발송은 취소한다. 수동 승인은 승인자의 현재 발송 권한이 유효해야 실행된다. 작업은 각 단계 시작과 외부 부작용 직전에 취소 세대와 권한을 확인한다. 확인 직후 이미 진행된 외부 요청은 회수/중단을 보장하지 않으며, 알려진 결과 또는 unknown을 감사 기록에 남긴다. 삭제가 요청된 회의는 진행 중 결과도 새로 공개하지 않고 정리한다.

웹훅 중복은 receipt 유일 키, 사용자 제출 중복은 idempotency key와 요청 해시로 처리한다. 완료 이벤트의 payload 전체를 장기 로그에 저장하지 않는다. 재시도는 지수 backoff·jitter·횟수/시간 상한을 둔다. 인증 오류는 재연결 필요, 4xx 입력 오류는 영구 실패, 429/5xx는 정책 내 재시도로 구분한다.

## 13. API 계약 초안

기본 경로 `/api/v1`. 인증·초대·웹훅 외 업무 API는 세션과 회사 membership 필수.

- `/auth/register|verify-email|login|logout|password-reset|session`
- `/organizations`, `/organizations/{org_id}/members|invitations|settings|usage`
- `/organizations/{org_id}/integrations/zoom/authorize`, `/integrations/zoom/callback`
- `/organizations/{org_id}/integrations/kakao/authorize`, `/integrations/kakao/callback`
- `/organizations/{org_id}/integrations/{id}` 상태 조회·연결 해제
- `/webhooks/zoom` 서명 검증 후 receipt/outbox 저장, 신속 응답
- `/organizations/{org_id}/meetings` 목록·수집 대상 등록·파일 업로드 등록
- `/organizations/{org_id}/meetings/{id}/transcript|minutes|recipients|jobs`
- `/organizations/{org_id}/meetings/{id}/minutes/{version}/pdf|approve|send`
- `/organizations/{org_id}/deliveries`, `/deliveries/{id}/retry` (회사 경로 하위)
- `/health/live`, `/health/ready` (비밀값·고객 데이터 미포함)

상태 변경은 POST/PATCH/DELETE, 페이지네이션·필터는 경계 검증. 응답 오류는 code/message/field_errors/request_id로 통일한다. 비동기 시작은 202와 job ID, 버전 충돌은 409. polling으로 작업 상태를 조회하며 첫 버전에서 WebSocket은 사용하지 않는다.

## 14. 보안·보관·운영

토큰은 서버 비밀키로 AEAD 암호화하고 key ID로 교체를 지원한다. 세션·OAuth state·초대 토큰은 암호학적 난수를 사용한다. 키는 .env 예시에 자리표시자만 기록하며 운영 시작 시 기본값/누락을 거부한다. 로그는 본문·비밀번호·토큰·서명 URL을 제외한다.

초기 제안 보관값은 녹음 7일, 녹취·회의록 90일, 메타데이터 감사 이력 180일이다. 회사가 짧게 변경할 수 있다. 삭제는 대기 작업/발송 취소 후 원본·파생 파일·DB 본문을 제거하고 개인 내용 없는 삭제 이력만 남긴다. 백업 보관·복구 시 재삭제 정책을 운영 문서에 명시한다. 회사 탈퇴/삭제와 단순 연동 해제는 구분한다.

녹음 및 외부 AI 전달 안내·처리 동의를 설정/업로드/자동화 활성화 흐름에 포함한다. 처리 중인 삭제 요청도 다음 단계에서 차단한다. 외부 API 호출 직전에 필요한 데이터만 전달한다.

관측 항목: 회사별 처리시간·실패율·전사분·LLM 토큰·큐 지연·unknown 발송·연동 만료. 원문 없이 request/job/meeting IDs로 추적한다. 무료 사용량 소진 시 대기/상한 초과를 표시하고 유료 플랜을 자동 구매하지 않는다.

## 15. 자동화 테스트·검증 전략

| 계층 | 도구 제안 | 핵심 검증 |
|---|---|---|
| Model | Vitest | 담당자·기한 표시, 검증, 권한별 동작 계산 |
| ViewModel | Vitest + Testing Library renderHook | 로딩/오류/재시도/취소, 중복 제출, 버전 충돌, 회사 전환 |
| View | Testing Library + MSW | 접근성·입력·상태 표시·API 계약 |
| 서버 단위 | pytest | 요약 스키마, 시간대, 파서, 발송 정책, 상태 전이 |
| DB 통합 | 실제 PostgreSQL/Redis 테스트 환경 | RLS·복합 FK·트랜잭션·outbox·동시 작업·리스 회수 |
| 어댑터 계약 | HTTP mock/SMTP 테스트 서버 | Zoom 서명·OAuth·토큰 교체·Groq 오류·카카오 접수·타임아웃 |
| E2E | Playwright | 가입/초대/2개 회사 격리/업로드/요약/승인/발송/권한 철회 |
| 문서 | PDF 텍스트 추출+페이지 렌더 확인 | 한국어 글꼴·긴 회의록·페이지 잘림·근거·버전 |

필수 실패 시나리오: 회사 ID 조작, 일반 직원 관리 API 접근, 만료/재사용 초대·OAuth state, CSRF, 원문 prompt injection, 다운로드 SSRF, 업로드 위장/초과, 중복/역순 웹훅, 잘못된 LLM JSON, 불명확한 동명이인, 429, 토큰 갱신 경쟁, 작업자 중단, 일부 채널만 성공, 외부 접수 후 타임아웃, 수정 후 낡은 승인, 삭제 후 잔여 발송.

CI는 format/lint/typecheck → 서버·프런트 단위 → DB 통합 → 프런트 빌드 → E2E 순으로 실행한다. 빠른 단위 테스트는 네트워크·실제 키 없이 실행한다. 외부 실연동 smoke 테스트는 별도 명령으로 분리하고, 사용자가 지정한 테스트 계정/수신자에만 실행한다. 소스 해시·명령·결과·미검증 항목을 검증 기록으로 남긴다. 테스트한 사실이 없는 성공 수치나 외부 연동 결과를 기록하지 않는다.

## 16. 구현 단계와 의사결정 경계

1. 이 문서 승인 후 구현 계획과 테스트 인수 목록을 작성한다.
2. 독립 meeting-agent 프로젝트와 실행 환경·CI·DB 마이그레이션을 준비한다.
3. 인증·회사 격리·초대·React MVVM 첫 세로 기능을 테스트하며 구현한다.
4. 업로드 → 전사 → 요약 → 회의록/PDF 경로를 완성한다.
5. Zoom OAuth/웹훅 자동 수집과 재처리 경로를 연결한다.
6. 승인·이메일·카카오 발송, 정책·보관·감사 이력을 연결한다.
7. 회사 간 침범·동시성·장애 복구·화면·문서를 검증하고 실행 안내를 제공한다.

첫 구현은 한 명의 통합 작성자가 담당하고, 읽기 전용 검토자를 별도로 사용한다. 작성자를 병렬화할 때는 독립 checkout을 먼저 배정한다. 공유 manifest/lockfile은 통합 작성자만 변경한다. 사용자 승인 없이 commit/push/배포/유료 사용/실제 직원 발송을 하지 않는다.

설계자가 정한 제안: 한국어 우선, 내부 직원만 수신, PDF+웹 문서, 직원별 카카오 본인 연결, 검토 후 발송 기본, 업로드 보완 경로, SMTP 서비스 주소 발송, 초기 파일/시간/보관 상한. 사용자는 설계 검토에서 이를 변경할 수 있다. 세부 UI 색상·개별 함수명·라이브러리 패치 버전은 구현자가 정한다.

## 18. 설계 검토 기록

독립 읽기 전용 builder 검토에서 자동 발송 승인 주체, 초안 공개 범위, 권한 철회 중 진행 작업, 근거 검증의 의미적 한계 네 항목을 지적했다. 설계자 제안으로 정책 버전 기반 시스템 승인, 일반 직원의 확정본만 열람, 단계 경계 차단과 외부 진행 요청의 회수 한계, 구조 검증과 의미 정확성의 구분을 추가했다. 이 기본값들은 사용자 설계 검토 대상이다.

작업 결정 기록: 사용자 요청에 따른 로컬 요구사항/설계 문서 작성만 허용한 범위에서 수행했다. 제품 코드·프로젝트 스캐폴딩·패키지 설치·실제 외부 발송·배포·commit/push는 수행하지 않았다. 새 프로젝트의 구현은 이 설계 승인 후 별도 구현 계획에 따른다.
